A plain-language interface to a client production database. We had a few dozen sample queries, no training set, and no database we were allowed to develop against, so most of the work happened before any modelling could start.

Building the dataset

Working with a graduate student, we built a synthetic database consistent with the client's samples, then generated 5,000 question–SQL pairs against it: programmatic generation for the query structures, LLM paraphrasing for natural-language variation, and manual validation throughout.

The interesting part is what went wrong. LLM paraphrasing collapses toward a house style. Programmatic generation produces queries no human would ask. Measuring coverage

A generated dataset can be large and still be narrow. I proposed measuring diversity through the distribution of pairwise cosine similarity between question embeddings, using its shape to find where generation was clustering, then correcting the sampling and regenerating. This is the most transferable idea from the project — coverage measurement matters wherever you build your own data, including simulation.

The system

We benchmarked open-source models — Qwen2.5, Llama and Codestral among them — and fine-tuned Qwen2.5, which performed best. The delivered system did not use the fine-tuned model: the client wanted the freedom to swap in a commercial API later, so we built a model-agnostic few-shot pipeline that draws on the training set without depending on any particular model's weights. It traded accuracy for the ability to change models without retraining.

My role

A graduate student led the project. I proposed the diversity and coverage metrics, worked on dataset generation and manual validation, and contributed to the model side — benchmarking open-source models, testing prompting strategies, and building out the inference pipeline.
